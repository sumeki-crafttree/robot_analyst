# ロボエコノミスト MVP 要件定義（概要 / System Requirements Overview）

**版**: v2.0（2026年8月24日 / MVP）
**上位文書**: [ミッション・ビジョン](01_mission_vision.md) / [要求定義](02_requirement_business.md)
**位置づけ**: 要求を、1週間・月1万円で実装可能なシステム要件へ翻訳する。詳細スキーマとIaCは下位の設計書・コードに委ねる。

---

## 1. 全体構成

- データパイプラインとWebアプリを**単一リポジトリ**に置き、Terraformで同じGCPプロジェクトへ展開する。
- データは `一次ソース → 生 → 加工 → プロダクト → レポート` の5段で流し、各段の責務を混ぜない。
- 各段は前段の出力のみを入力とし、後段から前段への逆流を禁止する。

| 段 | 実体 | 責務 |
|---|---|---|
| 一次ソース | TDnet / 各社IRサイト | 外部。取得のみ行い、加工しない |
| 生（raw） | GCS | 取得したファイルを原本のまま不変で保存する |
| 加工（staging） | BigQuery | 構造化・正規化する。解釈は加えない |
| プロダクト（mart） | BigQuery | 分析可能な形に整える。レポート生成の参照先 |
| レポート | GCS / Cloudflare Pages | 週次レポートを生成し配信する |

## 2. データソース要件

| ソース | 取得方式 | 更新頻度 | 用途 |
|---|---|---|---|
| 適時開示（決算説明資料含む） | TDnet | 随時 | 週次の新規性の主源。決算ポジショニングの数値源 |
| 競合各社のニュースリリース | 各社IRサイト | 随時 | 開示に至らない施策・値上げ・提携の検出 |

- 取得は冪等とし、同一期間を再実行しても生層が重複しないこと。
- **ニュースリリースの取得は各社サイト構造に依存するため、MVPでは対象を絞る。**
- 具体的には、RSS/Atomフィードを提供する企業を優先し、フィードのない企業は一覧ページのURLを設定として登録したうえで汎用の一覧抽出で処理する。
- 抽出に失敗した企業はスキップしてログに残し、パイプライン全体を止めないこと。

## 3. 要素技術の要件

| 要求（要求定義§4） | 満たすべき要件 |
|---|---|
| 関連各社のリストアップ | 対象企業の関連会社群を企業マスタとして保持し、追加・改廃を設定で行える |
| ライバル／パートナー／顧客の区別 | 企業マスタが自社から見た関係区分を属性として持つ |
| 関連各社の適時開示の抽出 | 企業マスタに含まれる企業の開示を漏れなく取得し、重要度で選別する |
| 自社への示唆の抽出 | 開示本文から、自社にとっての意味をイベントとして構造化する |
| マクロトピックへの各社アクション | トピック軸で各社の対応を横断比較できる形に集約する |

- **関連各社の初期リストは人手で作成する。**
- 判断根拠は、リストアップの自動化そのものが独立した開発項目であり、1週間の枠内で品質を担保できないためである。
- MVPでは30〜50社規模の初期マスタを人手で作り、以後の拡張・自動化を次フェーズに送る。

## 4. プロダクトデータセットのスキーマ要件

- 全レコードは一次ソースの識別子と原文位置を保持し、レポート上の記述から出所へ遡及できること。

| テーブル | 保持内容 |
|---|---|
| `dim_company` | 企業マスタ。自社から見た関係区分（ライバル／パートナー／顧客）を持つ |
| `dim_macro_topic` | 対象企業にとって重要なマクロトピックの定義 |
| `fact_disclosure` | 適時開示・ニュースリリースの原本メタデータ |
| `fact_insight` | 開示から抽出した自社への示唆。誰が・いつ・何を・自社にとっての意味 |
| `fact_topic_action` | マクロトピック × 企業のアクション。横断比較の入力 |
| `fact_financial_position` | 決算開示から抽出した同業比較用の財務値 |
| `mart_weekly_brief` | 週次レポートの生成入力。当週の差分を集約 |

## 5. レポート要件

**週次ハイライトレポート**

- 関連各社の当週の重要情報を、ライバル／パートナー／顧客の区分ごとに提示する。
- マクロトピックに対する各社のアクションを横断比較で示す。
- 各項目に自社への示唆を併記し、出所へのリンクを添える。

**決算ポジショニングレポート**

- 直近年度の決算開示において、自社が同業の中でどの位置にいるかを示す。
- 同業各社の決算開示が出揃ったタイミングで生成する。
- 週次と生成頻度が異なるため、同一パイプライン内の別ジョブとして実装する。

**配信**

- 生成物はGCSに版として保存し、Cloudflare Pagesで閲覧可能にする。
- 生成完了と失敗はメールで通知する。

## 6. 技術スタックとインフラ要件

- **GCP** — GCS（生・レポート）、BigQuery（加工・プロダクト）、Cloud Run Jobs（バッチ）、Cloud Scheduler（起動）、Secret Manager（認証情報）。
- **GitHub** — ソース管理とCI。mainへのマージでTerraformとジョブイメージを反映する。
- **Terraform** — 全インフラをコード化し、stateはGCSに置く。
- **Cloudflare** — Pagesでレポートを配信し、ドメインとDNSを管理する。
- 認証情報はSecret Managerのみに置き、リポジトリへコミットしない。

## 7. コスト要件（上限 月1万円）

| 項目 | 想定 | 月額 |
|---|---|---|
| GCS | 数GBの原本保存 | 約100円 |
| BigQuery | 無料枠（保存10GB／クエリ1TB）内 | 0円 |
| Cloud Run Jobs | 週次バッチ、無料枠内 | 0円 |
| Cloud Scheduler | ジョブ2本、無料枠内 | 0円 |
| Cloudflare Pages | 無料プラン | 0円 |
| LLM API | 示唆抽出＋レポート生成 | 3,000〜6,000円 |
| 予備 | 再実行・試行分 | 残り |

- **変動費はLLM API利用料のみであり、ここが唯一の超過リスクである。**
- 開示件数に比例して増えるため、**用途でモデルを分ける**。
- 開示の選別・示唆抽出は件数が多いため安価なモデルを用い、週次レポートの文章生成のみ高性能モデルを用いる。
- 1回の実行に投入するトークン量に上限を設け、超過時は処理を中断してアラートを出す。

## 8. 非機能要件

- **遡及可能性** — レポートの全記述が一次ソースまで辿れること。
- **冪等性** — 同一週の再実行が重複データを生まないこと。
- **網羅性** — 企業マスタに含まれる企業の当週の適時開示に、取りこぼしがないこと。
- **拡張性** — 対象企業の追加が `dim_company` への行追加と設定変更で完結すること。
- **部分失敗耐性** — 一部ソースの取得失敗がパイプライン全体を止めないこと。
- **コスト可観測性** — 月次の実績コストを確認でき、上限接近時に気づけること。

## 9. 実装順序（7日間）

| 日 | 実施内容 |
|---|---|
| 1 | リポジトリ構成、Terraformでのプロジェクト・GCS・BigQuery・Secret Manager構築 |
| 2 | 企業マスタの初期作成、TDnet取得の実装（生層まで） |
| 3 | ニュースリリース取得の実装、加工層（生→BigQuery staging） |
| 4 | プロダクト層。示唆抽出とマクロトピック集約 |
| 5 | 週次ハイライトレポートの自動生成と配信 |
| 6 | 決算ポジショニングレポート |
| 7 | Cloud Schedulerでの自動実行、通しテスト、コスト実測 |

- 遅延した場合に削る順序は、①決算ポジショニングレポート、②ニュースリリース取得、③マクロトピック横断比較とする。
- 判断根拠は、週次ハイライトが成立していれば顧客に届ける価値が立つのに対し、他は上積みであるためである。
- **週次ハイライトの自動生成と配信（Day 5まで）は死守する。** ここが崩れるとMVPの成功基準を満たさない。
