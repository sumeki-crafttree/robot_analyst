## 1. 設計方針

- **すべての判断を、1週間で作れるかとコストで裁く。** 将来の拡張性は、いま複雑さを増やす理由にしない。
- **状態を持つのはGCSとBigQueryだけにする。** ジョブは常にステートレスとし、再実行で同じ結果に収束させる。
- **LLMを呼ぶ箇所を1つに限定する。** 呼び出し箇所が増えるほどコストと不確実性が乗算で増える。
- **マネージドサービスの無料枠内に収まる構成を選ぶ。** 常時起動するコンポーネントを持たない。

## 2. システム構成

```text
                    ┌──────────────┐
   Cloud Scheduler ─┤ daily 07:00  ├─→ Cloud Run Job: ingest-daily
   (asia-northeast1)│ weekly Mon 08│─→ Cloud Run Job: report-weekly
                    └──────────────┘
                             │
        ┌────────────────────┼────────────────────┐
        ↓                    ↓                    ↓
   ┌─────────┐        ┌─────────────┐      ┌──────────────┐
   │   GCS   │        │  BigQuery   │      │Secret Manager│
   │ original│        │ raw         │      │ LLM API key  │
   │ raw     │        │ processed   │      │ CF API token │
   │ report  │        │ product     │      └──────────────┘
   └─────────┘        └─────────────┘
        │                    │
        └─────→ report-weekly ┘
                     │
                     ↓
            Cloudflare Pages（Access で保護）
```

- リージョンは **asia-northeast1** に統一する。TDnetが国内ソースであり、レイテンシと転送料の両面で有利なため。
- 常時起動するコンポーネントを持たない。Cloud Run Jobsは実行時のみ課金される。

## 3. リポジトリ構成

データパイプラインとWebアプリを単一リポジトリに置く（02§6）。

```text
.
├── infra/                    Terraform
│   ├── main.tf
│   ├── variables.tf
│   ├── storage.tf            GCS バケット
│   ├── bigquery.tf           データセット・テーブル
│   ├── run.tf                Cloud Run Jobs
│   ├── scheduler.tf          Cloud Scheduler
│   ├── secrets.tf            Secret Manager
│   └── iam.tf                サービスアカウント・権限
├── pipeline/                 Python
│   ├── ingest/               TDnet取得 → original
│   ├── transform/            テキスト化 → raw
│   ├── extract/              LLM抽出 → processed
│   ├── load/                 processed → product
│   ├── report/               product → HTML
│   └── common/               設定・ログ・BQクライアント
├── schema/
│   ├── bigquery/             テーブルDDL
│   └── llm/                  structured output スキーマ
├── web/                      Cloudflare Pages 配信物のテンプレート
├── data/master/              シードCSV（UTF-8 BOM付き）・JPXマスタ
├── docs/                     本書を含むドキュメント
└── .github/workflows/        CI/CD
```

- `pipeline/` の各サブパッケージは、6層のうち1層ぶんの変換のみを担う。層をまたぐ処理を書かない。
- コンテナイメージは1つとし、エントリポイントの引数でジョブを切り替える。**イメージを分けない理由は、ビルド時間とArtifact Registryの保存量を抑えるため**である。

## 4. ストレージ設計

### 4.1 GCS

| バケット | 用途 | ライフサイクル |
|---|---|---|
| `{project}-original` | TDnet原本（PDF/XML） | 90日でNearlineへ移行 |
| `{project}-raw` | テキスト化済み中間物 | 180日で削除 |
| `{project}-report` | 生成済みレポート（版管理） | 削除しない |

オブジェクトパスは日付で分割し、再実行時の範囲指定を容易にする。

```text
original/dt=2026-09-01/{disclosure_id}.pdf
raw/dt=2026-09-01/{disclosure_id}.txt
report/weekly/2026-W36/report.html
```

- **`original` にはバージョニングを有効化する。** 03§8の再生成可能性は、原本が失われないことに全面的に依存するため。
- `raw` を削除しても `original` から再生成できるため、保存期間を短くしてコストを抑える。

### 4.2 BigQuery

| データセット | 内容 |
|---|---|
| `raw` | テキスト化済み開示。1開示1行 |
| `processed` | LLM出力とvalidation結果。中間 |
| `product` | 04§5の6テーブルと参照用View |

- ロケーションは `asia-northeast1`。
- `processed` にはパーティション有効期限を180日で設定し、保存量を抑える。`product` には設定しない。

## 5. データモデル物理設計

04§5の論理定義を、BigQueryの物理設計に落とす。

| テーブル | パーティション | クラスタリング |
|---|---|---|
| `dim_company` | なし | なし |
| `dim_macro_theme` | なし | なし |
| `fact_disclosure` | `DATE(disclosure_datetime)` | `company_id` |
| `fact_extracted_fact` | `fact_date` | `company_id`, `company_action` |
| `fact_theme_mapping` | なし | `fact_id` |
| `fact_implication` | `DATE(created_at)` | `target_company_id` |

- 週次レポートは直近1週間のみを読むため、日付パーティションが常に効く。**BigQueryのクエリ課金を無料枠内に収める設計上の要**である。
- `relationship_type` と `business_area` は `ARRAY<STRING>`。ブリッジテーブルを追加せず6テーブル構成を維持する（6.3）。

### 5.1 主キーとID生成

BigQueryは制約を持たないため、IDの一意性はアプリケーション側で担保する。

| ID | 生成規則 |
|---|---|
| `disclosure_id` | TDnetの開示IDをそのまま使う |
| `fact_id` | `SHA256(disclosure_id + ':' + seq)` の先頭16桁 |

- **`fact_id` を決定的に生成する。** 同一開示を再処理したときに同じIDが再現され、MERGEで重複を防げるようにするため（8章）。

### 5.2 参照用View

```sql
CREATE VIEW product.v_fact_enriched AS
SELECT
  f.fact_id, f.fact_date, f.effective_date, f.summary,
  c.company_name, c.relationship_type, c.business_area,
  f.company_action, f.action_status, f.direction,
  f.quantitative_value, f.quantitative_unit,
  ARRAY(SELECT t.theme_code FROM product.fact_theme_mapping m
        JOIN product.dim_macro_theme t USING(macro_theme_id)
        WHERE m.fact_id = f.fact_id) AS macro_themes,
  i.implication, i.expected_direction,
  f.extraction_confidence, i.inference_confidence,
  f.evidence_text, d.title, d.original_uri
FROM product.fact_extracted_fact f
JOIN product.fact_disclosure d USING(disclosure_id)
JOIN product.dim_company c ON c.company_id = f.company_id
LEFT JOIN product.fact_implication i USING(fact_id);
```

- 02§3の「開発者が毎日使って嬉しい」を満たすための唯一のView。これを引けば6テーブルのJOINを書かずに済む。

## 6. マスタ設計

### 6.1 なぜこのマスタが最重要か

- 03§3が述べるとおり、**マスタの網羅性がプロダクトの網羅性の上限を直接決める**。
- 04§8のパイプラインでは、TDnetの全開示をこのマスタと突合し、一致しない開示を破棄する。
- したがって、マスタにない企業の開示は**構造的に、恒久的に拾えない**。後段をどれだけ改善しても回復しない。
- 同時にこれはコスト制御の要でもある。突合をLLM呼び出しより前に置くことで、対象外企業にLLMを呼ばない。

### 6.2 セクターの決定

- 対象企業はニチレイ（02§2）であり、セクターは**食品**で確定している。
- ただし**マスタ自体は単一セクターに閉じない。** ニチレイのバリューチェーンを辿ると、包装資材（金属製品）、物流（陸運業）、販売チャネル（小売業）へ必然的に広がる。
- 初期100社の内訳は、17業種区分で 食品45・小売27・商社卸売11・運輸物流8・素材化学4・情報通信2・電力ガス2・建設資材1 の8業種にまたがる。
- **マスタの選定軸は業種ではなく、対象企業との関係である。** 業種で切ると、値上げの波及を追ううえで不可欠な包装資材メーカーや外食チェーンが落ちる。

### 6.3 スキーマ

| カラム | 型 | 必須 | 内容 |
|---|---|---|---|
| `company_id` | STRING | ○ | 証券コード。英数字を許容する（例: `130A`） |
| `company_name` | STRING | ○ | JPXマスタ上の名称 |
| `is_target` | BOOL | ○ | 対象企業本体か |
| `relationship_type` | ARRAY\<STRING\> | ○※ | `peer` / `partner` / `customer`。複数可 |
| `priority` | STRING | ○※ | `high` / `mid` / `low`。レポートでの優先度 |
| `business_area` | ARRAY\<STRING\> | ○ | 対象企業と接する事業領域 |
| `jpx_sector_17` | STRING | | 17業種区分 |
| `jpx_sector_33` | STRING | | 33業種区分 |
| `note` | STRING | | 選定理由・注記 |

※ `is_target = true` の行のみ `relationship_type` を空とする。自社に対する関係区分は定義しないため。

- **`priority` は100社規模にしたことで必要になった列である。** 31社の時点では全社を等しく扱えたが、100社では週次レポートに載る件数が増え、ニッスイと地方スーパーを同列に並べると読めなくなる。レポート生成時の並び順と、分量が多い週の足切りに用いる。
- `company_id` を **INT64にしてはならない。** JPXは2024年以降、英数字混在のコード（`130A` 等）を発行している。実際にJPXマスタ内に存在する。
- `relationship_type` と `business_area` は配列とし、04§5の6テーブル構成を崩さない（ブリッジテーブルを追加しない）。
- シードCSVでは配列を `|` 区切りで表現し、ロード時に分割する。
- **シードCSVの文字コードは UTF-8 with BOM とする。** ExcelはBOMを見てUTF-8と判定するため文字化けせず、同時にVS Code・GitHub・BigQueryといったUTF-8前提のツールでもそのまま読める。Shift-JISにすると前者しか満たせない。
- 読み込み側はBOMを除去すること。Pythonでは `encoding='utf-8-sig'` を指定する。

### 6.4 relationship_type の判定基準

MVPでは3区分のみを用いる（04§4.4）。判定は**企業単位**で行い、事業セグメント単位には分解しない。

| 区分 | 判定基準 |
|---|---|
| `peer` | 同一の最終需要に対して、代替関係にある製品・サービスを提供している |
| `partner` | 自社の供給網の上流にあるか、事業運営に不可欠な財・サービスを提供している |
| `customer` | 自社の製品・サービスの販売先、または需要家である |

**複数該当する場合は、該当するすべてを付与する。** 実際に初期100社のうち5社が複数区分に該当する。

- 味の素 — 冷凍食品で競合しつつ、調味料・アミノ酸の供給側でもある
- NIPPON EXPRESSホールディングス — 低温物流で競合しつつ、幹線輸送では協業関係にある
- ヤマトホールディングス — クール便で競合しつつ、宅配網では協業関係にある
- SGホールディングス — 同上
- センコーグループホールディングス — 食品3PLで競合しつつ、庫内業務では協業関係にある

この5社は、単一区分に押し込むと実態を失う。配列で持つ設計の妥当性を示す実例として、初期マスタに意図的に含めている。

**「その他」区分は設けない。** 3区分のいずれにも当てはまらない企業は、そもそもマスタに入れる根拠がない。

### 6.6 選定根拠

**peer（40社）** — 冷凍食品・中食・低温物流の3系統で選定した。冷凍食品はニッスイ・Ｕｍｉｏｓ・極洋に加え、**日東ベストと大冷という業務用冷凍食品の専業2社を含めている。この2社はニチレイの業務用事業に対する最も直接的な競合でありながら、規模が小さく見落とされやすい。** 中食・惣菜・チルドを17社と厚くしたのは、冷凍食品の代替がチルド・惣菜であり、需要が両者の間を移動するためである。低温物流9社は、ニチレイが食品専業ではなくニチレイロジグループを持つことを反映する。横浜冷凍とキユーソー流通システムが最も近い。

**partner（32社）** — 04§4.1の `macro_theme` のうち `input_cost` と `logistics` に直結する供給側を選んだ。油脂4社（不二製油・日清オイリオ・J-オイルミルズ・ミヨシ油脂）と製粉3社（日清製粉G・ニップン・昭和産業）を厚くしたのは、**食品各社の値上げ開示で理由として最も頻出する原料だからである。** 包装資材はFPコーポレーション（食品トレー）を含め6社。エネルギーは東京電力HDと東京ガスで、冷凍倉庫の電力と加熱工程の燃料に対応する。原料商社（ラクト・ジャパン、スターゼン、ニチモウ）は、原料価格の変動が食品各社より先に開示に現れるため、先行指標として機能する。

**customer（32社）** — 家庭用（量販・CVS・EC）と業務用（外食・卸）の両チャネルを代表させた。量販16社は全国チェーンと地域スーパーを混在させ、地域ごとの消費動向の差が拾えるようにしている。**食品卸3社（トーホー・加藤産業・ヤマエグループHD）を入れたのは、卸が量販と外食の両方に接しており、需要の変化が小売各社より早く開示に現れることがあるためである。** 外食13社は、業務用冷凍食品の需要家として客数・価格改定の動向を追う。

**意図的に外した企業** — ローソン（2651）と日本通運（9062）は上場廃止済みで、TDnetに開示が出ない。テーブルマークとファミリーマートは非上場であり、親会社（JT・伊藤忠）で拾うとたばこ・商社の開示ノイズが大半を占める。飲料・菓子の専業各社は、冷凍食品との需要の代替性が低いため含めていない。

**31社から100社への拡張理由** — 期中開示に処理対象を絞った結果、週次レポートに載る件数が2〜7件/週まで下がる見込みとなった（10.4）。LLM呼び出しはこの規模でも月100回程度に留まり、コスト上限に対して十分な余裕がある。**企業数を決めるのはコストではなく選定品質である**という原則に従い、関係が説明できる範囲で100社まで広げた。

### 6.7 保守方針

- 追加・改廃は **`data/master/dim_company_seed.csv` への行編集のみ**で完結する（03§8 拡張性）。
- 名称と証券コードは**JPXマスタを正とする。** 記憶や過去資料を典拠にしない。
- JPXマスタは四半期ごとに更新し、差分を確認する。
- 抜けが判明した時点で行を追加する。遡及して過去の開示を取り込むかは、04§8のジョブを対象期間指定で再実行するかどうかで決める。

**社名変更の検知が必要な理由** — 本設計時、1333を記憶に基づき「マルハニチロ」と記載しかけたが、JPXマスタ上の2026年6月末時点の商号は **Ｕｍｉｏｓ** であった。社名変更は珍しくなく、突合を証券コードで行う設計であれば実害はないが、レポートに旧社名が出ると顧客の信頼を損なう。名称はマスタ更新のたびに上書きする。

### 6.8 品質基準と既知の限界

**品質基準**

- `company_id` がJPXマスタに実在すること。ロード時に検証する。
- `is_target = true` の行が、ちょうど1件存在すること。
- `is_target = false` の全行に `relationship_type` が1件以上あること。

**既知の限界**

- 初期マスタは人手で作成しており、網羅性の保証がない（03§3）。10社は「実用に足るか」を検証するための出発点であり、完成形ではない。
- 関係区分は企業単位で付与しており、セグメント単位の粒度を持たない。ニチレイの低温物流セグメントに対してのみ競合である企業も、企業全体として `peer` になる。
- 非上場の重要な取引先（テーブルマーク、ファミリーマート等）は、適時開示を出さないため構造的に扱えない。これは適時開示を唯一のソースとする設計（02§5）の帰結である。

**稼働後の確認事項**

- BigQueryへのロード処理を04§8のステップ2に組み込む。
- 稼働後、TDnetの全開示に対する突合ヒット率を計測する。ヒット率が低すぎる場合はマスタの拡張を、高すぎる場合はノイズの混入を疑う。
- 10社での検証を経て、30〜50社規模への拡張可否を判断する。

## 7. ジョブとLLM呼び出し設計

### 7.1 ingest-daily

日次 07:00 JST。04§10のステップ1〜6を1ジョブで実行する。

```text
1. TDnetから前日分の開示一覧を取得
2. 対象企業の原本を GCS original へ保存（source_type を問わず全件）
3. dim_company と company_id で突合し、対象外企業を除外      ← 絞り込み①
4. source_type で絞り込み、四半期資料を以降から除外          ← 絞り込み②
5. PDF/XMLをテキスト化し GCS raw と BQ raw へ
6. LLMを1開示1回呼び、processed へ
7. validation を通過した行を product の6テーブルへMERGE
```

- **ステップ3と4をLLM呼び出しより前に置くことが、コスト設計の中核である。** TDnetの日次開示は全体で数百件あるが、100社に該当するのは十数件に留まり、うち期中開示はさらに絞られる。
- **ステップ2だけは絞り込みの対象外とし、四半期資料もoriginalへ落とす。** MVPでは処理しないが、Phase 2で遡って処理できるようにするためである（04§3）。TDnetは過去開示の取得可能期間に制限があり、取得しそびれると回復できない。
- タイムアウトは30分、メモリ2GiB、CPU 1。

### 7.2 report-weekly

週次 月曜 08:00 JST。

```text
7. product から前週分（月〜日）を集約
8. LLMでレポート本文を生成
9. HTMLを GCS report へ版として保存
10. Cloudflare Pages へデプロイ
11. 完了をメール通知
```

- ingest-daily の完了を前提とするが、**ジョブ間の依存はスケジュール時刻の差で担保する**。ワークフローオーケストレータ（Workflows / Composer）は導入しない。1週間で作る規模に対して過剰であり、Composerは常時課金でコスト上限を超えるため。

### 7.3 共通事項

- 両ジョブとも同一コンテナイメージを使い、`--job=ingest|report` で切り替える。
- 実行結果は `product.ops_run_log` に1実行1行で記録する（12章）。

### 7.4 モデルの使い分け

| 用途 | モデル | 呼び出し数 |
|---|---|---|
| ファクト抽出・分類・示唆付与 | 安価モデル | 1開示につき1回 |
| 週次レポート本文の生成 | 高性能モデル | 1週につき1回 |

- 03§7の「用途でモデルを分ける」の実装。件数が出るのは抽出側であり、文章品質が要るのは生成側であるため、要求が正反対になる。

### 7.5 抽出呼び出し

- structured output を用い、04§6.2のJSONスキーマを強制する。
- `temperature = 0`。同一入力に対する出力のばらつきを抑え、再生成の再現性を確保する。
- 入力は開示本文のみとし、マスタや過去データを文脈に入れない。**入力を固定することで、トークン量が開示の長さだけで決まり、見積り可能になる。**
- 本文が長い場合は先頭から一定トークンで打ち切る。要約してから渡すことはしない（要約自体がLLM呼び出しを増やすため）。

### 7.6 リトライ

- schema validation 失敗時は1回だけリトライする（04§7.2）。
- リトライ時はエラー内容をプロンプトに付加する。
- 2回失敗した場合は `status = failed` で記録し、ジョブは継続する。

### 7.7 コストガード

- 1実行あたりの累積入力トークンに上限を設ける。
- 上限に達した時点で処理を中断し、`ops_run_log` に記録してメール通知する。
- **上限は「異常検知」であって「常用の節約手段」ではない。** 通常運転で上限に触れる場合は、設計の見直しが必要という信号として扱う。

### 7.8 冪等性と再生成

- すべての書き込みを `MERGE` で行い、`INSERT` を使わない。
- キーは `disclosure_id` および `fact_id`。`fact_id` は決定的に生成される（5.1）。
- 同一日の再実行は、同じ入力から同じIDを生成し、既存行を上書きする。行は増えない。
- **再生成の起点は常に `original` である。** モデル変更・プロンプト変更・taxonomy変更のいずれの場合も、`original` から対象期間を再処理する。
- 再処理は日付範囲を引数に取る。`--from=2026-08-01 --to=2026-08-31` のように指定する。
- LLMを再度呼ぶため、再処理の実行回数は `ops_run_log` に記録し、無制限に回さない（03§7）。

## 8. レポート配信設計

- `report-weekly` が静的HTMLを生成し、GCSへ `report/weekly/{ISO週}/report.html` として保存する。
- 同じHTMLを Cloudflare Pages へ Direct Upload でデプロイする。
- **Cloudflare Access でアクセスを保護する。** レポートには対象企業向けの分析が含まれるため、公開URLに置いてはならない。Accessは無料枠で50ユーザーまで利用でき、追加コストが発生しない。
- 過去版はGCSに残す。Pagesには最新版のみを置く。
- 完了通知のメールは、レポートのURLと当週のファクト件数を含む。

## 9. インフラ・CI/CD・セキュリティ設計

### 9.1 Terraform

- stateはGCSバケット `{project}-tfstate` に置く。バージョニングを有効化する。
- 環境は本番1つのみとする。**開発環境を分けない理由は、1週間の構築期間に対して二重管理のコストが見合わないため**である。
- 手動で作成するのはGCPプロジェクトとtfstateバケットのみ。それ以外はすべてTerraformで管理する。

### 9.2 GitHub Actions

| ワークフロー | トリガ | 内容 |
|---|---|---|
| `ci` | PR | lint、テスト、`terraform plan` |
| `deploy` | mainへのpush | イメージのビルドとpush、`terraform apply` |

- GCPへの認証は Workload Identity Federation を用いる。**サービスアカウントキーをGitHub Secretsに置かない。**

### 9.3 セキュリティ

- 秘密情報はSecret Managerのみに置く。対象はLLM APIキーとCloudflare APIトークン。
- サービスアカウントはジョブ用に1つ作成し、以下の最小権限のみを付与する。
  - GCS: 対象バケットへの `objectAdmin`
  - BigQuery: 対象データセットへの `dataEditor`、ジョブ実行の `jobUser`
  - Secret Manager: 対象シークレットへの `secretAccessor`
- GCSバケットはすべて非公開とし、Uniform bucket-level accessを有効化する。
- レポートの公開はCloudflare Accessの背後に限る（9章）。

## 10. 運用設計と規模見積り

### 10.1 実行ログ

`product.ops_run_log` に1実行1行で記録する。

```text
run_id, job_name, started_at, finished_at, status,
disclosures_fetched, disclosures_matched, facts_written,
llm_calls, input_tokens, output_tokens, estimated_cost_jpy,
error_count, error_summary
```

- このテーブルが、03§8の「コスト可観測性」の実体である。GCPの課金画面を見に行かなくても、SQLで月次の推移を追える。

### 10.2 通知

- ジョブ失敗時、およびコストガード発動時にメール通知する。
- 正常時は週次レポートの完了通知のみを送る。日次の成功通知は送らない。**通知が日常になると、異常時に気づかなくなるため。**

### 10.3 監視すべき指標

| 指標 | 見方 |
|---|---|
| `disclosures_matched / disclosures_fetched` | 突合ヒット率。低すぎればマスタ不足、高すぎればノイズ混入 |
| `facts_written / disclosures_matched` | 1開示あたりのファクト数。0が続けば抽出が機能していない |
| `error_count` | 継続的な増加はTDnet側の形式変更を疑う |
| `estimated_cost_jpy` | 月次で1万円に対する消化率 |

### 10.4 規模見積り

**以下はすべて推計であり、稼働後の実測で置き換える。**

| 項目 | 見積り | 根拠 |
|---|---|---|
| 対象企業数 | 100社 | 6.5の初期マスタ |
| original層へ保存する開示 | 約800〜1,100件/四半期 | 1社あたり8〜11件/四半期。四半期資料を含む |
| うち四半期資料 | 約200件/四半期 | 100社 × 短信1 + 説明資料1 |
| **うちMVPの処理対象（期中開示）** | **約100〜300件/四半期** | 実質的な内容を持つ期中開示。1社あたり1〜3件/四半期 |
| 週次レポートに載る件数 | 約8〜23件/週 | 期中開示は通年に分散する |
| LLM呼び出し | 約33〜100回/月 | 処理対象の期中開示数に一致 |
| BigQuery保存量 | 1GB未満/年 | テキストは`raw`、原本はGCS |

- **期中開示に絞ったことで、週次の分量が平準化する。** 決算発表期（5月・8月・11月・2月）に集中するのは四半期資料62件であり、これを処理対象から外したため、平常週と決算期の差が大幅に縮む。
- ただし業績予想修正（`forecast_revision`）は決算期に寄るため、振れが完全に消えるわけではない。
- **1件あたりのトークン量も下がる。** 期中開示は1〜3ページ、決算説明資料は30〜50ページであり、10〜20倍の差がある。件数では四半期資料が4割でも、トークン量では8〜9割を占めていた。
- LLM呼び出しが月33〜100回に留まるため、**コスト上限に対する制約はマスタの企業数ではない。** 企業数を決めるのはマスタの選定品質であって、コストではない。
- **週8〜23件という分量は、週次レポートとして妥当な水準である。** 31社時点の2〜7件/週では薄かったため、100社へ拡張した（6.6）。
- ただし上振れ時の23件は、レポートとして読み切れる上限に近い。`priority` による並び替えと足切りで対応する（6.3）。
