**出所**: エンジニアからのレビュー
**対象**: [要求定義](../01_mvp/02_requirement_business.md) §5 / [パイプライン要件定義書](../01_mvp/04_requirement_system_detail.md) §3 / [プロダクト設計書](../01_mvp/05_product_design.md)
**結論**: 採用。02・04・05へ反映済み。

---

## 1. フィードバックの要旨

適時開示を2系統に分けて扱うべきである。

**四半期開示資料系**（決算短信・決算説明資料・業績説明資料）

- 情報量が多く、マクロ環境・業績影響・経営対応がまとまっている。
- 定点観測・因果分解・対応方針の把握に向く。
- 「原材料高→利益率低下→価格改定を推進」のような流れが取れる。
- 一方で経営者の総括や後付け説明が多く、**イベントの発生時点が曖昧になりやすい**。

**期中の個別開示系**（価格改定・設備投資・新拠点・工場停止・M&A・事業撤退・災害影響・業績予想修正）

- 情報量は少ないが、**「誰が・何を・いつ・どれくらいやるか」が明確**。
- イベント検知・転換点検知・企業アクションの構造化に向く。

**提案：MVPは期中開示を主ソースとする。** 理由は3点。

1. 抽出対象が明確である。`event_type` / `company_action` / `action_status` / `effective_date` / `target_product_or_business` / `quantitative_value` / `reason` が比較的きれいに取れる。
2. 企業横断で比較しやすい。「ニッスイが冷凍食品を2〜30%値上げ」「日清オイリオが食用油を11〜21%値上げ」「競合物流会社が冷凍物流拠点を新設」を同一のイベントテーブルに乗せられる。
3. 汎用AIとの差別化がしやすい。四半期資料を大量に読ませて要約するだけなら上位LLMでも相当できる。期中開示を継続監視し、発生イベント→共通分類→企業アクション→バリューチェーン上の意味→顧客企業へのrelevanceとして時系列蓄積するほうが、プロダクト固有のデータ資産になる。

**ただし最終的には四半期資料も入れるべきである。役割が違う。**

```text
期中開示  「9月から値上げ」
   ↓
Q資料    「原材料高で採算悪化、価格転嫁を進めた」
   ↓
次のQ資料 「価格改定効果で利益率改善」
```

つまり、**期中開示 = Event Stream、四半期資料 = State / Context Snapshot** である。

開発順序は、Phase 1で期中開示だけでイベントDBを作り、Phase 2で四半期資料を追加してイベントの背景・結果を補完する。

## 2. レビュー結果

採用する。既存設計との整合性が上がる方向の指摘である。フィードバックに書かれていない支持根拠を3点補足する。

**2.1 04§6.3「1開示1ファクトを基本とする」が、これで初めて成立する**

抽出スキーマ（04§6.2）は `company_action` / `action_status` / `effective_date` / `direction` / `quantitative_value` を1セット持つ形であり、期中開示を前提とした設計になっている。決算説明資料を同じスキーマに通すと1資料から10〜30個のファクトが出て、既定の粒度が破綻する。

**2.2 週次レポートの分量が平準化する**

05で「決算期は平常週の5〜10倍に振れる」と指摘していた。振れの正体は31社の決算短信と説明資料62件が2〜3週に集中することである。期中開示は通年に分散するため、四半期資料を処理対象から外すと振れ幅がほぼ消える。

| 系統 | 件数/四半期（31社） | 分布 |
|---|---|---|
| 四半期資料 | 約62件 | 2〜3週に集中 |
| 期中の実質開示 | 約31〜93件 | 通年に分散 |

**2.3 LLMコストの大半は四半期資料側にある**

期中開示は1〜3ページ、決算説明資料は30〜50ページで、1件あたりのトークン量が10〜20倍違う。件数では四半期資料が4割でも、トークン量では8〜9割を占める。05§7.5の「本文が長い場合は先頭から一定トークンで打ち切る」処理も、期中開示に絞ればほぼ不要になる。

---

## 3. 修正した点

**3.1 「二次ソース」ではなく「Phase 2で処理対象に加える」と整理する**

データソースとしては同じTDnetであり、違うのは処理対象かどうかだけである。「一次ソース/二次ソース」という言い方は実装時に曖昧になる。

**3.2 四半期資料もoriginal層には最初から取り込む。処理だけしない**

03§1の「original以外の全層はoriginalから再生成できる」という原則により、取得しておけばPhase 2で過去に遡って処理できる。**取得しなければ過去分は永久に失われる。TDnetは過去開示の取得可能期間に制限があるため、これは後から戻せない差になる。**

---

## 4. 決定事項

- MVPの処理対象は**期中の個別開示**（`timely_disclosure`・`forecast_revision`）とする。
- 決算短信・決算説明資料（`earnings`・`earnings_presentation`）は**取得のみ行い、MVPでは処理しない**。Phase 2で処理対象に加える。
- スキーマ変更は行わない。04§3の `source_type` 表に処理フェーズの列を追加するのみで足りる。
