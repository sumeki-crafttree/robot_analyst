## 背景

適時開示のタイトルは当たり障りのない定型文であり、本文の実質を表さない。「固定資産の譲渡および特別利益の計上に関するお知らせ」というタイトルの裏に、「構造改革で熊本の生産機能を松山へ移管、譲渡益61億円」という内容がある。

本文を読んで1文のメッセージを生成し、文書単位の属性として持たせる。読み手は**ヘッジファンドのアナリストおよびトレーダー**である。

## 設計の要点

【マクロテーマ付与とは別パスにする】

同じLLM処理ですが、3点が異なります。同一コールに統合しないでください。

                  マクロテーマ付与        アナリストメッセージ
  対象            ゲート通過分のみ(約60%)  全文書
  入力            キーワード周辺のスパン    本文冒頭（約2,000字）
  出力の粒度      1文書N行                1文書1行
  ゲート          適用する                適用しない

ゲートを適用しない理由は、マクロ要因を含まない開示にもメッセージの価値が
あるためです。井関農機の工場売却はマクロテーマがゼロですが、メッセージと
しては有用です。

入力を冒頭にする理由は、適時開示が定型で「記」の直後に理由・内容・日程が
並ぶためです。スパン抽出はマクロ語彙に依存するため、この用途には使えません。

プロセスは分けないでください。モデルのロードに時間がかかるため、
tag_macro_theme.py の実行内で別パスとして動かします。

【コンテキスト文書を実行時に読む】

  notebook/prompts/analyst_message_v1.txt      構造（入力の与え方・出力形式）
  notebook/context/hedge_fund_analyst_v1.md    内容（誰が読むか・何が価値か）

プロンプトには構造だけを書き、「何を重視するか」はコンテキスト文書に置いて
実行時に読み込んでプロンプトへ差し込んでください。読み手を経営企画部に
切り替える場合、コンテキスト文書を差し替えるだけで済むようにします。

コンテキスト文書の内容をプロンプトファイルへ複写しないでください。
二重管理になります。

【出力】

文書単位の属性として持たせます。

  analyst_message           生成された1文。40〜80字
  message_materiality       high / medium / low / none
  message_numbers_verified  メッセージ中の数値がすべて原文に存在するか
  message_model             使用モデル
  prompt_version            analyst_message_v1
  context_version           hedge_fund_analyst_v1

prompt_version と context_version を両方記録してください。どちらを変えて
結果が変わったのかを切り分けるために必要です。

【数値の検証】

アナリスト向けにおいて、誤った数値は無いことより悪いです。

  1. 生成後、メッセージから数値表現を抽出する
  2. すべてが原文に存在するか機械的に検証する
  3. 表記ゆれ（61億円 と 6,100百万円）を吸収するため正規化して比較する
  4. 存在しない数値があれば1回だけ再生成する
  5. 再度失敗したら message_numbers_verified = false を立てて記録する

【生成しない場合】

  - 本文が空（スキャンPDF等）
  - issuer_kind が etf_etn / reit_fund
    日次基準価額の転記でありメッセージが成立しません

## キックオフ時に推奨する初期判断

**1. `message_materiality` をLLMに判定させるか、ルールで決めるか**

`source_type` と本文の定型表現（「影響は軽微」「軽微であります」）である程度は機械的に決まる。一方、金額規模の大小はLLM判断になる。**まずLLMに判定させ、分布を見てからルール併用を検討する**のが順当である。

**2. 数値抽出の正規化範囲**

最低限、次を吸収する。

```text
億円 / 百万円 / 千円 / 円     単位の換算
1,234 / 1234                  桁区切り
全角数字 / 半角数字            字種
約61億円 / 61億円              概数表現
```

過剰に作り込まない。**検証で弾かれた件数を見てから範囲を広げる。**

**3. 処理量の確認**

全文書が対象のため、テーマ付与より対象が多い。

| | 件数/日 | E4B | 12B |
|---|---|---|---|
| マクロテーマ付与（ゲート後） | 約262 | 0.6h | 1.8h |
| アナリストメッセージ（全件） | 約426 | 約0.9h | 約3.0h |
| 合計 | | 約1.5h | 約4.8h |

12Bで両方を日次実行すると1日4.8時間のGPU使用となり、Colab無料枠の割当時間に収まらない可能性が高い。**費用の問題ではない**（ローカル推論のためトークン課金は発生せず、Gemma自体も無料）。制約はGPUを動かせる時間だけである。層化サンプルでの試行はE4Bと12Bの両方で行い、一致率を見る。
