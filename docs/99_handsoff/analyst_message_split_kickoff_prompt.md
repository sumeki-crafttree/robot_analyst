# アナリストメッセージ生成の分離 キックオフプロンプト

**種別**: 既存実装のリファクタ（機能追加ではない）
**対象**: `notebook/tag_macro_theme.py` から分離 → `notebook/generate_analyst_message.py` を新設
**関連**: [アナリストメッセージ生成 詳細設計](../01_design/03_analyst_message_design.md) §3 / [実装時のキックオフ](analyst_message_kickoff_prompt.md)

## 背景

アナリストメッセージ生成は `tag_macro_theme.py` に `--with-message` として実装された（commit `0437630`）。結果として同ファイルが2,245行になり、**スクリプト名と機能が一致しなくなった。**

「マクロテーマを付与する」という名前のスクリプトが、マクロテーマと無関係なメッセージ生成も行っている状態である。これを独立スクリプトへ分離する。

**機能の追加や変更は行わない。動作は現状を維持する。**

## 使い方

以下の「プロンプト本文」を新しいセッションへ貼り付ける。**純粋なリファクタである。** 出力が変わってはならない。

```text
対象リポジトリ: /Users/pgin/Git/021_robot_analyst

# 依頼

独立したスクリプト notebook/generate_analyst_message.py へ分離してください。

## 読むもの

docs/01_design/03_analyst_message_design.md の §3（テーマ付与との違い）

分離する理由と、共通化してはいけない理由が書いてあります。

## なぜ分離するか

tag_macro_theme.py が2,245行になり、「マクロテーマを付与する」という名前の
スクリプトがメッセージ生成も行っている状態です。名前と機能が一致していません。

対象・入力・出力の粒度がいずれも異なります。

                  マクロテーマ付与        アナリストメッセージ
  対象            ゲート通過分のみ         全文書
  入力            キーワード周辺のスパン    本文冒頭（約2,000字）
  出力の粒度      1文書N行                1文書1行
  ゲート          適用する                適用しない

## 作業内容

1. notebook/generate_analyst_message.py を新設し、メッセージ生成に関する
   処理を移設する

   移設対象（tag_macro_theme.py 内の該当箇所）:
     MESSAGE_* / CONTEXT_* の定数群
     プロンプトとコンテキストの読み込み
     本文冒頭の切り出し（MESSAGE_BODY_CHARS / MESSAGE_LEAD_CHARS）
     メッセージ生成のLLM呼び出しとGBNF文法
     数値検証（message_numbers_verified）
     materiality 別の目視確認用サンプル出力
     出力JSONLの書き出し

2. tag_macro_theme.py から上記を削除し、--with-message オプションも削除する
   マクロテーマ付与だけを行うスクリプトに戻す

3. 出力ファイルを分ける
     macro_themes_{yyyymmdd}.jsonl      tag_macro_theme.py
     analyst_messages_{yyyymmdd}.jsonl  generate_analyst_message.py

## 守ること

【重複を許容する】

  LLM実行部（llama-cpp-pythonの初期化、モデルのロード、GBNF文法の組み立て、
  リトライ処理）は2本のスクリプトで重複します。これは意図的です。

  共通モジュールに切り出さないでください。既存3本は「Colabに1セル貼り付けて
  動く」形を保っており、import が増えるとこれが壊れます。設計方針から
  外れます。

【モデルのロードが二重になることを許容する】

  2本を続けて実行すると、モデルのロードが2回発生します（各1.5〜6分）。
  これは許容します。可読性と責務の一致のほうが価値が高いという判断です。
  ロード時間を惜しんで1本にまとめないでください。

【動作を変えない】

  - 分離前後で、同じ入力に対して同じ出力が出ること
  - prompt_version / context_version / model の記録を維持
  - 数値検証のロジックを変えない
  - 再開可能性（1件ごとの追記保存、処理済みスキップ）を維持
  - 実行モード（--sample / --date / --from-to）を両スクリプトで維持

【既存の規約を維持】

  - Colab前提（_ensure_dependency、ROOT_DIR定数）
  - ログ機能（LOG_DIR、_log_path、_log_header、_Tee）を新スクリプトにも実装
  - CSVはUTF-8 with BOM、encoding='utf-8-sig'
  - data/prompts/ と data/context/ からの読み込みパスは変えない

## やらないこと

- メッセージ生成のロジック変更、プロンプト変更、コンテキスト文書の変更
- マクロテーマ付与のロジック変更
- 共通モジュールの作成
- ゲート語彙の修正（別タスク）

## 完了条件

1. tag_macro_theme.py が --with-message を持たず、マクロテーマ付与のみを行うこと
2. generate_analyst_message.py が単体でColabに貼り付けて動くこと
3. 分離前に生成した出力と、分離後の出力が一致すること
   （層化サンプル300件で比較。同じモデル・同じプロンプトなら
     temperature=0 のため一致するはずです）
4. 両スクリプトの行数が分離前より読みやすくなっていること
5. 新スクリプトのログがDriveに残ること
```

## キックオフ時に推奨する初期判断

**1. 出力の一致をどう確認するか**

分離前の出力を退避してから作業を始める。`temperature = 0` かつ GBNF制約下であれば、同じモデル・同じプロンプトで出力は一致するはずである。**一致しない場合、移設漏れか切り出し位置のずれを疑う。**

**2. 重複するコードの範囲を先に決める**

移設前に、`tag_macro_theme.py` のどの関数がメッセージ専用で、どれが共通かを列挙する。GBNF文法の組み立てはテーマ用とメッセージ用で構造が違うため、**共通に見えて実は別物である**箇所に注意する。

**3. 実行順序の依存**

2本とも前処理JSONLを入力とし、相互に依存しない。**どちらを先に実行してもよい設計にする。** 日次運用では順不同で回せることが望ましい。
