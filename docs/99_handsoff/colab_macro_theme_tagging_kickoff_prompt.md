## プロンプト本文

```text
対象リポジトリ: /Users/pgin/Git/021_robot_analyst

# 依頼

Google Colab（無料枠・T4）上で動く2本のPythonスクリプトを実装してください。
目的は、適時開示PDFからマクロテーマを付与し、分類体系が実際に機能するかを
数値で検証することです。

## 最初に読むもの

1. docs/01_design/02_colab_prototype_design.md  ← 本実装の設計。全章
2. docs/01_design/01_macro_theme_tagging_pipeline.md  ← 上位設計。5章と6章
3. notebook/tdnet_pdf_preprocessing.py  ← 参考にする既存実装（940行）

設計書と矛盾する実装をしないでください。設計書に書かれていない判断が必要に
なった場合は、実装を止めて質問してください。

## 作るもの

1. notebook/build_sample.py
   取得済みの全開示から層化サンプル300件を抽出し、文書IDリストを
   data/samples/ に保存する（設計書 8.2）
   ※これは試行用のテストフィクスチャです。運用は日次全件です。

2. notebook/preprocess_disclosures.py
   PDF → 1文書1行のJSONL（設計書 4章）

3. notebook/tag_macro_theme.py
   前処理JSONL → マクロテーマ付与JSONL（設計書 5章）

2と3は3つの実行モードを持たせてください（設計書 8.2）。
  --sample            層化サンプル300件。プロンプト・モデルの試行用
  --date YYYY-MM-DD   指定日の全開示。日次運用の本番モード
  --from/--to         期間指定。バックフィル用

本番の運用形態は「毎日、その日の全開示（約426件）にタグを付ける」です。
層化サンプルは試行用であって運用モードではありません。日次運用が
第一級のユースケースとして動くように作ってください。

4. notebook/prompts/macro_theme_v1.txt
   プロンプト本体。コード内の文字列リテラルにしないこと（設計書 7.2）

## 前提

- 過去30日の全開示PDF（約9,400件・約4.7GB）はDriveに取得済みです。
  notebook/fetch_tdnet_metadata.py を DOWNLOAD_PDFS=True で実行したものです。
  このファイルは変更しないでください。
- Google Driveは2TBあり、容量制約はありません。制約はT4のVRAM 16GBだけです。

## 絶対に守ること

【既存コードの扱い】
- notebook/tdnet_pdf_preprocessing.py の処理ロジック（PyMuPDFのブロック抽出、
  pdfplumberのテーブル抽出、ページレイアウト判定、ヘッダフッタ除去、文字列正規化）
  は変更せず、そのまま流用してください。
- 変えるのは出力形式だけです。現行は1文書6ファイルですが、1文書1行のJSONLに
  します。理由はDriveでの小ファイル大量生成が極端に遅いためです。
- 動作実績のある部分に手を入れると、検証したいこと（分類体系が機能するか）と
  壊れた原因の切り分けができなくなります。

【Colab環境】
- 既存コードのColab前提（_ensure_dependency()による実行時pip、ROOT_DIR定数）は
  維持してください。requirements.txt化はGCP移行時の話であり、今回は不要です。
- T4はbfloat16に非対応です。float16を使ってください。
- T4はFlash Attention 2に非対応です。
- 依存に cryptography を必ず含めてください。TDnetにはAES暗号化PDFが混じり、
  これがないとテキスト抽出が失敗します。件数が少ないため握り潰されると
  気づきません。

【推論】
- transformers + bitsandbytes ではなく、llama.cpp（llama-cpp-python）を
  使ってください。
- 出力はGBNF文法で制約してください。これが最重要です。Gemmaにはネイティブの
  structured output機能がなく、文法制約なしだとJSONパース失敗が頻発します。
- GBNFのコード選択肢（l1code, l2code）は、候補L1に応じて実行時にマスタCSVから
  動的に生成してください。これによりマスタに存在しないコードを返す失敗が
  構造的に起きなくなります。
- モデルは Gemma 4 12B の Q4_K_M GGUF を第一候補とします。E4Bも同じ
  インターフェースで差し替えられるようにしてください（速度比較のため）。

【スパン抽出】
- 決算短信は平均13,855字、決算説明資料は11,703字あります。全文をLLMに
  投げないでください。精度も速度も出ません。
- マクロ語彙のヒット位置から前後1ブロックを連結してスパンを作り、
  スパンのみを渡してください。既存コードの EVIDENCE_CONTEXT_WINDOW と
  同じ考え方で、キーワード配列をマスタ語彙に差し替えれば流用できます。
- ゲートでヒットしたL1のみをプロンプトに載せてください。16テーマ全部を
  載せる必要はありません（実測で1文書平均3.2個）。

【再開可能性】
- Colabのセッションは切れます。1件処理するごとに追記保存してください。
  全件終了後にまとめて書き出す設計にしてはいけません。
- 起動時に出力JSONLを読み、既に処理済みのdocument_idはスキップしてください。
  これは必須要件です。

【マスタの読み込み】
- data/master/dim_macro_theme_seed.csv （101行）
  L1 16件とL2 85件が1ファイルに入っています。level列（L1/L2）で判別してください。
  L1行のみ definition / includes / excludes を持ち、L2行は空です。
- UTF-8 with BOMです。encoding='utf-8-sig' を指定してください。
  BOMを除去しないと1列目のカラム名が壊れ、突合が全件失敗します。

## やらないこと

- ウォッチ企業と関連企業の関係（peer/partner/customer）の付与
- 企業アクション・定量値の抽出、自社への示唆のマッピング
- レポート生成、GCS/BigQuery/Terraform/Cloud Run
- 30日分のバックフィル一括処理（12Bで40時間かかります。試行は層化サンプル300件で
  行ってください。日次1日分426件なら1.8時間で成立します）
- 軽量モデルへの置き換えや蒸留

data/samples/tdnet_bodies_202608.jsonl に、100社の開示236件の本文が
保存されています（PDFから抽出済み）。tag_macro_theme.py の動作確認は、
PDFを経由せずこのファイルを入力にして行えます。前処理を待たずに
プロンプトの試行に入れます。

## 完了条件

層化サンプル300件に対して前処理と付与が完走し、セッション断があっても
再開して完了できること。そのうえで以下が数値で出ること。
これが本実装の目的です。「動いた」ではなく数値が成果物です。

- source_type別のゲート通過率（実測値 timely 34.5% / forecast 50.0% /
  earnings 95.9% / presentation 92.6% と整合するか）
- ゲート通過分のうち実際にテーマが付いた割合（ゲートの誤検出率）
- L1別の付与件数（全く付かないテーマは定義かゲート語彙の問題）
- L1別のL2 null率（高いテーマはL2定義の不足）
- other率（高ければ分類体系の欠落）
- GBNF適用下でのスキーマ違反件数（原則ゼロのはず）
- 1件あたり処理時間

加えて、各L1につき3件ずつ付与結果を抽出し、evidence_textが本当にその
テーマを述べているか人が読める形で出力してください。数値だけでは
誤分類の質が分かりません。
```

## キックオフ時に推奨する初期判断

プロンプト実行後、最初に次の4点を決めると進めやすい。

**1. GGUFの入手元**

`unsloth/gemma-4-12b-it-GGUF` の UD-Q4_K_XL を第一候補とする。手製のQ4_0変換は精度が落ちるため避ける。`ggml-org` の公式変換も選択肢。

**2. llama-cpp-python のCUDAビルド**

Colabでは `CMAKE_ARGS="-DGGML_CUDA=on" pip install llama-cpp-python` が必要。CPUビルドが入ると `n_gpu_layers=-1` が効かず、推論が数十倍遅くなる。**インストール直後にGPU層がロードされていることをログで確認する手順を入れる。**

**3. スパン抽出の初期値**

```text
前後ブロック数        1（既存の EVIDENCE_CONTEXT_WINDOW と同じ）
1スパンの上限         1,200字
1文書のスパン合計上限   4,000字
```

これらは調整対象である。設計書5.2の値を初期値とし、テーマ付与率が低い場合に広げる。

**4. 日次運用に使うモデル**

日次426件はゲート通過262件、12Bで1.8時間・E4Bで0.6時間。前処理27分を加えると
12Bでは1日2.3時間となり、**Colab無料枠のGPU割当上限に抵触する可能性が高い**。

したがってE4Bと12Bの比較は「E4Bで足りるか」ではなく「**日次運用をE4Bで回せるか**」
という問いである。品質が同等なら速度3倍のE4Bが運用上の第一候補になる。
12Bは層化サンプルでの品質基準として使う。

**5. プロンプトv1の粒度**

まず「候補L1を3つ程度、そのL2一覧、スパン、few-shot 1件」で始める。精度が出ない場合は、設計書6.4の次善策（候補L1ごとにYes/Noを個別に問う形式）へ切り替える。呼び出し回数は増えるが小型モデルには易しい。

## 補足：この実装単位の位置づけ

本実装は**分類体系の検証が目的**であり、本番パイプラインではない。GCP版の設計は `docs/01_design/01_macro_theme_tagging_pipeline.md` にあるが、**そちらの実装は本検証の数値が出てから着手する**。分類体系が作り直しになった場合の手戻りを避けるためである。
