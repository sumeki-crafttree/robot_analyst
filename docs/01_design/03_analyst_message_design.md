# 詳細設計：アナリストメッセージ生成

**版**: v0.1（2026年9月10日）
**上位文書**: [Colab検証環境 詳細設計](02_colab_prototype_design.md)
**位置づけ**: 開示本文から、読み手にとって意味のある一文を生成する機能の設計。02と矛盾する場合は02が優先する。
**実装**: `notebook/generate_analyst_message.py`（独立スクリプト）

---

## 1. 背景と目的

**適時開示のタイトルは当たり障りのない定型文であり、本文の実質を表さない。**

実データでの落差は大きい。

| タイトル | 本文にある実質 |
|---|---|
| 味の素「吸収合併に関する基本方針についてのお知らせ」 | 電子材料事業の成長加速を目的とした子会社の吸収合併 |
| 一正蒲鉾「持株会社体制への移行に伴う吸収分割契約締結」 | 水産練り製品業界で倒産・売却による再編が進行しており、他業界を巻き込んだ合従連衡を想定した体制構築 |
| 井関農機「固定資産の譲渡および特別利益の計上」 | 構造改革で熊本の生産機能を松山へ移管、工場跡地を譲渡し譲渡益61億円 |
| AZ-COM丸和HD「連結子会社間の組織再編」 | 連結業績への影響は軽微 |

タイトルだけを見て「法人格の整理であって事業の動きではない」と評価した開示にも、本文には業界認識が書かれていた。**タイトルは事象の種別を示すが、実質は示さない。**

本機能は、本文を読んで**1文のメッセージ**を生成し、文書単位の属性として保持する。

## 2. 読み手の定義

**ヘッジファンドのアナリストおよびトレーダーを読み手とする。**

これは設計上の分岐点である。同じ開示でも、経営企画部向けなら「自社への示唆」、アナリスト向けなら「株価に効くか」が基準になる。**読み手が変わればメッセージの内容が変わる。**

読み手の定義とメッセージの品質基準は、**コードやプロンプトに埋め込まず、外部のコンテキスト文書として持つ**（4章）。読み手を切り替える際に、プロンプトの構造を変えずに済ませるためである。

## 3. テーマ付与との違い

同じLLM処理でありながら、3点が異なる。**同一コールに統合せず、別パスとする。**

| | マクロテーマ付与 | アナリストメッセージ |
|---|---|---|
| 対象 | ゲート通過分のみ（約60%） | **全文書** |
| 入力 | キーワード周辺のスパン | **本文冒頭（約2,000字）** |
| 出力の粒度 | 1文書N行（テーマ言及） | **1文書1行** |
| ゲート | 適用する | **適用しない** |

- **ゲートを適用しない理由**は、マクロ要因を含まない開示にもメッセージの価値があるためである。井関農機の工場売却はマクロテーマがゼロだが、メッセージとしては有用である。
- **入力が冒頭である理由**は、適時開示が定型で「記」の直後に理由・内容・日程が並ぶためである。決算短信のような長文でも、要旨は冒頭にある。スパン抽出はマクロ語彙に依存するため、この用途には使えない。
- **統合しない理由**は、入力も対象も異なるためである。無理に1コールにまとめると、双方の品質が落ちる。

**独立したスクリプトとする。** `notebook/generate_analyst_message.py` を新設し、`tag_macro_theme.py` からは分離する。

- 判断根拠は、**スクリプト名と機能が一致していることを優先する**ためである。`tag_macro_theme.py` に `--with-message` として同居させると、名前が実態を表さなくなり、2,000行を超えて読めなくなる。
- **モデルのロード時間が二重に発生することは許容する。** 1回あたり1.5〜6分であり、試行の妨げにはならない。可読性と責務の一致のほうが価値が高い。
- 既存スクリプトと同様、**単体でColabに貼り付けて動く形を保つ**。LLM実行部（llama-cpp-pythonの初期化、GBNF文法の組み立て）が `tag_macro_theme.py` と重複するが、共通モジュール化はしない。**共通化すると単体貼り付けができなくなり、既存3本の設計方針から外れる。**

## 4. コンテキスト文書

**読み手の定義・評価軸・良い例と悪い例を、実行時に参照する外部文書として持つ。**

```text
data/context/hedge_fund_analyst_v1.md    読み手の定義と品質基準
data/prompts/analyst_message_v1.txt      プロンプトの構造
```

いずれも `data/` 配下に置く。マクロテーマのプロンプトと同じ並びであり、Driveへ `data/` を上げるだけで実行環境が揃う（02§7.2）。

- プロンプトは**構造**（入力の与え方、出力形式の指定）のみを持ち、**内容**（何を重視するか）はコンテキスト文書に置く。
- 読み手を経営企画部に切り替える場合、コンテキスト文書を差し替えるだけで済む。プロンプトは変更しない。
- 出力には `context_version` と `prompt_version` の両方を記録する。**どちらを変えて結果が変わったのかを切り分けるため**である。

## 5. 出力

`fact_disclosure` に文書単位の属性として持つ。出力先はマクロテーマ付与と分ける。

```text
data/processed/
├── macro_labeled/{model}__{macro_prompt_version}/{yyyymmdd}/
│       macro_themes_{yyyymmdd}.jsonl   tag_macro_theme.py
└── analyst_messages/{model}__{analyst_message_version}/{yyyymmdd}/
        analyst_messages_{yyyymmdd}.jsonl   generate_analyst_message.py
```

`run_tag` を日付の上に置くのは、モデルとプロンプト版ごとに結果を丸ごと分けて比較するためである（02§9）。

```json
{
  "document_id": "20260831_6310_a1b2c3d4",
  "analyst_message": "井関農機、構造改革で熊本の生産機能を松山へ移管し工場跡地を譲渡。譲渡益61億円を2027年12月期1Qに計上",
  "message_materiality": "medium",
  "message_numbers_verified": true,
  "message_model": "gemma-4-12b-it-Q4_K_M",
  "prompt_version": "analyst_message_v1",
  "context_version": "hedge_fund_analyst_v1"
}
```

| 項目 | 内容 |
|---|---|
| `analyst_message` | 生成された1文。40〜80字 |
| `message_materiality` | `high` / `medium` / `low` / `none`。読み手にとっての重要度 |
| `message_numbers_verified` | メッセージ中の数値がすべて原文に存在するか（6.3） |

## 6. 生成の要件

### 6.1 入力

- 本文の先頭から2,000字。ただし「記」が出現する場合はその前後を優先する。
- タイトル、会社名、`source_type`、業種を併せて渡す。**同じ内容でも業種によって読み手の関心が変わる**ためである。

### 6.2 品質基準

コンテキスト文書に記載するが、要点は次のとおり。

- **主語を書く。** 「当社」ではなく会社名。
- **言い切る。** 「〜について」「〜に関するお知らせ」で終えない。
- **数値を入れる。** 本文にあれば必ず含める。比較の基準（前年比、発行済株式数に対する割合、通期計画に対する割合）が本文にあれば併記する。
- **P&Lに効く時期を書く。** 「2027年12月期1Qに計上」のように。
- **重要でないものは重要でないと書く。** 「連結業績への影響は軽微」はそれ自体が読み手にとって有用な情報である。**無理に意味を作らない。**

### 6.3 数値の検証

**アナリスト向けにおいて、誤った数値は無いことより悪い。**

- 生成後、メッセージから数値表現を抽出し、**すべてが原文に存在するかを機械的に検証する**。
- 存在しない数値が含まれる場合は1回だけ再生成する。再度失敗したら `message_numbers_verified = false` を立てて記録する。
- 表記ゆれ（`61億円` と `6,100百万円`）を吸収するため、正規化して比較する。

### 6.4 生成しない場合

- 本文が空（スキャンPDF等）の場合は生成しない。
- `issuer_kind` が `etf_etn` / `reit_fund` の場合は生成しない。日次基準価額の転記であり、メッセージが成立しない。

## 7. 処理量

全文書が対象のため、テーマ付与より対象が多い。

| | 件数/日 | E4B | 12B |
|---|---|---|---|
| マクロテーマ付与（ゲート後） | 約262 | 0.6h | 1.8h |
| **アナリストメッセージ（全件）** | **約426** | **約0.9h** | **約3.0h** |
| 合計 | | **約1.5h** | 約4.8h |

- **12Bで両方を日次実行すると1日4.8時間のGPU使用となり、Colab無料枠の割当時間に収まらない。** これは費用の問題ではない。**ローカル推論のためトークン課金は発生せず、Gemma自体も無料である**（02§2）。制約はGPUを動かせる時間だけである。
- したがってE4Bでの運用を前提とし、12Bは層化サンプルでの品質基準として使う。Colab Proに切り替える場合は12Bでも成立し、L4が使えれば 26B A4B も選択肢に入る。
- 入力が冒頭2,000字に固定されるため、テーマ付与よりトークン量の振れが小さい。

## 8. 受入基準

- 層化サンプル300件に対してメッセージが生成されること。
- 以下が数値で出ること。

| 指標 | 見方 |
|---|---|
| `message_numbers_verified` が false の割合 | 高ければ数値のハルシネーション。プロンプトかモデルの問題 |
| `message_materiality` の分布 | `high` が多すぎれば重要度の判定が甘い |
| 文字数の分布 | 40〜80字に収まっているか |
| タイトルとの重複率 | タイトルを言い換えただけのメッセージが多くないか |

**目視確認を必ず行う。** `materiality` 別に各5件を人が読み、読み手（アナリスト）にとって意味があるかを判断する。**この機能の品質は数値だけでは測れない。**

とりわけ次を確認する。

- タイトルを言い換えただけになっていないか
- 本文にない解釈を足していないか
- 「影響は軽微」を無理に意味のある話にしていないか
